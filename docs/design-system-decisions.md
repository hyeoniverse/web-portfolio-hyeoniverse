# 디자인 시스템 결정 기록

> [명세](./design-system.md)의 규칙을 **왜** 그렇게 정했는지와 그동안의 이력. 규칙 자체는 명세에만 적는다.
> 새 결정은 맨 아래에 번호를 이어 붙인다. 뒤집힌 결정은 지우지 않고 "→ D번호로 바뀜"을 단다.

---

### D1. CSS Modules + 토큰 하나로 간다 (Tailwind 를 되돌림)

Tailwind 를 한 번 들였다가 같은 flex 행이 어디는 `tw:flex`, 어디는 `styles.row` 인 상태가 됐다. 두 방식이
반반 섞이면 어느 쪽이 기준인지 아무도 모른다. 이 사이트는 커스텀 애니메이션·GSAP·Three.js·정교한 CSS 효과가
핵심이라 컴포넌트마다 맞춘 CSS 가 유리하고, 토큰 체계도 이미 있었다. RSC 에 안전하고 런타임 비용이 없다는 것도
CSS Modules 쪽 이점이다.

### D2. 토큰 층은 셋

모듈 안의 `--_*` 를 네 번째 층으로 적어 뒀는데 실제로 쓰는 컴포넌트가 0곳이라 뺐다. Material(ref → sys → comp),
Spectrum(global → alias → component)도 세 층이다.

### D3. 간격에 조합 토큰을 두지 않는다

`--box-xs-md` 같은 여백 조합 토큰이 119개까지 불었고 84개가 안 쓰였다. 65개로 줄여도 근본 문제는 남았다 —
`--box-2xs-sm` 은 "4px 12px" 라는 값만 말하고 **왜 그 여백인지**는 말하지 않는다. Carbon·Atlassian·Polaris
어디에도 조합 토큰은 없다. 눈금 두 개를 나란히 적고, 반복되는 컴포넌트 종류에는 역할 토큰(`--card-p-md` 등)을 준다.
간격 눈금 사이 값(3px·6px 등) 106곳은 가까운 눈금으로 붙였다(최대 4px 차이).

### D4. 컴포넌트 여백 역할 토큰을 만드는 법

뱃지 118곳이 29가지 여백을 썼다. 이름만 통일하면 숫자는 안 준다. 등급을 글자 크기로 나눴더니(12px → md,
13px → lg) `StatusBadge` 가 넓어져 관리자 표의 Edit 단추를 침범했다 — 같은 13px 이라도 표 안 상태 뱃지는
조밀해야 하고 누르는 태그 필터는 넉넉해야 한다. 그래서 **각 자리에서 가장 가까운 등급**으로 붙였다. 이동이 가장
적고, 이미 맞는 자리는 이름만 바뀐다. 4px 넘게 떨어진 곳은 의도로 보고 두었다. 목록 행도 33종 → 3종. 가로
여백이 0인 행은 부모가 좌우를 주므로 제외했다. 모달·카드·입력 필드도 같은 방법.

### D5. 컨트롤 높이를 하나로

`--button-h-*`(20/24/38/46), `--control-h-*`(24/28/32/36), `_sizing.css` 주석의 "계층"(24/32/38/46)이 같은
"컨트롤 높이"를 다르게 말했다. 같은 `size="md"` 가 자리에 따라 32px 이기도 38px 이기도 했다. 공용 Button·Input 이
실제로 쓰던 `--control-h-*` 를 남기고 나머지를 흡수했다(렌더는 그대로). 흡수하면서 2xs·xl·2xl 이 들어와 간격이
고르지 않게 됐다 → D12 에서 정리.

### D6. 모서리는 셋 → D16 으로 바뀜

2px ~ 42px 눈금이 열세 개 있었고, 같은 성격의 카드가 6px 과 12px 로 갈렸다. 쓰는 곳이 0인 단계는 지우고,
컴포넌트가 고르는 건 capsule · circle · 2xl 셋으로 줄였다.

### D7. 글자 크기에 역할 이름 → D20 으로 바뀜(크기만이 아니라 글자 묶음 역할, 24px 이상도 역할)

14px 이하 네 단계는 원래 그 역할(본문·라벨·힌트·마이크로)을 위해 있던 값이라 1:1 로 역할 이름을 줬다.
16·18·20px 에만 `title-*`·`body-*` 이름을 붙인 건, 이 구간에서만 같은 크기를 제목과 본문이 같이 쓰기 때문이다.
24px 부터는 전부 제목·디스플레이라 단계 이름이 곧 역할이다.

### D8. 지운 토큰들

`--fluid-spacing-*` 11개(사용 0), `--breakpoint-*` 7개(사용 0 — 미디어 쿼리는 `var()` 를 못 받는다).

### D9. Button 과 Pressable 을 나눔

생김새를 통일하면 안 되는 자리가 많다 — 절대위치 클릭 영역, 부모 글꼴을 물려받는 페이지 번호, 필터 행 높이에 맞춘
탭. 그 자리들이 놓치던 건 생김새가 아니라 **동작**이었다(사운드 없음, `type` 없어 폼 안에서 제출 — 63곳,
disabled 제각각). 동작만 `Pressable` 로 떼었다. `react/button-has-type` 은 셋 중 하나만 막는다.

### D10. 다른 파일 클래스를 `composes` 하지 않는다 (#632)

두 모듈의 단일 클래스가 한 요소에서 겨루면 승자는 소스 순서다. 개발 서버는 import 순서대로 한 청크에 담고,
배포 빌드는 Turbopack 이 청크를 나눈 뒤 `experimental.inlineCss` 로 다시 싣는다 — 같은 코드가 개발과 배포에서
다르게 보였다. 같은 파일 안 `composes` 도 두 단계째는 Turbopack 이 안 붙인다.

### D11. 2026-10-01 — 명세를 다시 씀

이전 문서는 방향(3층·조합 금지·역할 이름·lint 강제)은 업계 관례와 맞았지만, 실무 기준으로 낡거나 틀린 판단이
있었고, "막는다"고 적은 규칙 상당수를 lint 가 실제로 막지 않았다. 다시 쓰면서 바꾼 것:

| | 이전 | 지금 | 근거 |
|---|---|---|---|
| 문서 형태 | 규칙·이유·이력·값이 한 파일 | 명세 · 결정 기록 · 토큰 표(자동 생성) | 손으로 옮긴 값이 어긋났다(모션 시간 문서 250/400/600ms, 실제 300/500/800ms) |
| 규칙 상태 | 전부 "금지" | 강제 / 목표(남은 수) / 권장 | lint 는 색 다섯 속성의 hex 만 봤고 z-index·모션·숫자 모서리는 막지 않았다 |

### D12. 컨트롤 높이 눈금 정리 (예정)

### D13. 2026-10-02 — 눈금은 미리 전부, 지우는 건 역할·조합 토큰만

D11 의 2-7 은 "쓰는 순간 추가하고, 안 쓰게 되면 지운다"를 모든 토큰에 거는 것처럼 읽혔다. 눈금(`--font-size-*`
`--spacing-*` 등)은 단계가 고르게 다 있어야 골라 쓸 수 있어서 쓰는 곳이 0이어도 남긴다(2-6). "쓸 때 추가·안 쓰면
삭제"는 역할·컴포넌트 토큰에만, 조합 토큰은 아예 만들지 않는 것으로 범위를 나눴다. 안 쓰는 토큰 102개 중
눈금 단계 35개는 남기고 67개만 정리 대상이다.

### D14. 2026-10-02 — 11px(`micro`)과 12px(`hint`)을 둘 다 둔다 → D15 로 바뀜

1px 차이지만 나눈다. 조밀한 자리(달력 칸·표 안 뱃지·카운터)에서는 8% 차이가 줄바꿈을 가른다. Apple(Caption 2 11 /
Caption 1 12)·Material(label-small 11 / body-small 12)도 같은 둘을 둔다.
다만 이전 문서의 근거 "못 읽어도 되는 것"은 틀렸다 — 실제로 103곳 중 달력 요일·일정 이름·입력 글자 수처럼 읽어야
하는 자리가 많다. 기준을 "문장이냐 짧은 라벨이냐"로 바꿨다: 문장은 12px 이상, 11px 은 숫자·카운터·요일 같은 짧은 라벨만.
"12px 하한"이라면서 11px 토큰이 있던 모순도 "문장의 하한 12 / 숫자로 쓸 수 있는 하한 12, 11 은 토큰으로만"으로 정리했다.

### D15. 2026-10-02 — 11px 단계를 없앤다 (D14 를 뒤집음)

D14 는 조밀한 자리의 1px 을 근거로 11·12 를 둘 다 뒀지만, 1px 차이의 두 단계는 고르는 기준이 "문장이냐 라벨이냐"
같은 해석에 기대게 되고 실제로도 섞여 쓰였다(달력 요일·일정 이름 같은 읽어야 하는 글자에 11px). 가장 작은 글자를
12px 하나로 정하고, 조밀한 자리는 글자 크기가 아니라 여백·줄 수·말줄임으로 푼다.
`--font-size-micro` 를 쓰는 103곳을 `--font-size-hint` 로 옮긴 뒤 토큰과 눈금 `3xs`(11px)를 지운다(이행 8단계).

### D16. 2026-10-02 — 모서리도 눈금 + 역할로 (D6 을 바꿈) → D20 에서 일부 바뀜(원은 `--radius-full`, 역할 셋)

D6 은 "고르는 건 capsule·circle·2xl 셋"을 눈금 이름으로 정하고 쓰지 않는 단계(`lg` 12 · `xl` 16 등)를 지웠다.
그러자 눈금이 2·4·6·8 다음 24 로 건너뛰어 2-6(눈금은 미리 전부)과 어긋났고, 각진 것이 의미인 자리 19곳은 규칙 위반 주석을
달고 눈금을 직접 써야 했으며, "안쪽 = 바깥 − 여백" 권장은 정작 그 사이 값을 쓰지 못했다.
"셋만"은 눈금 규칙이 아니라 역할 규칙이었다. 글자 크기처럼 눈금은 빠짐없이 두고(`lg`·`xl` 을 되살린다), 컴포넌트는
역할 토큰 넷(`control`·`surface`·`round`·`mark`)만 쓴다(`lg`·`xl` 은 D19 때 실제로 되살렸다 — 그 전까지 문서 표에만 있었다). 지금 눈금 이름을 직접 쓴 1176곳은 이름만 바꾸면 되고 보이는 건 그대로다.

### D17. 2026-10-02 — `-webkit-backdrop-filter` 를 쓰지 않는 진짜 이유

접두어를 붙였을 때 크롬에서 블러가 사라지는 일이 두 번 있었다(5월 토스트·홈 CTA, `bc9af356` 에서 일괄 제거).
이전 문서는 "크롬 파서가 꼬인다"고 적었지만, 크롬은 모르는 접두어 선언을 무시할 뿐이다. 원인은 빌드다.
Next(Turbopack)가 쓰는 Lightning CSS(1.33)는 `backdrop-filter` 와 `-webkit-backdrop-filter` 를 같은 속성으로 보고
**뒤에 적힌 하나만 남긴다.**

| 원래 CSS | 빌드 결과 |
|---|---|
| `backdrop-filter: blur(16px); -webkit-backdrop-filter: blur(16px)` | `-webkit-backdrop-filter: blur(16px)` 만 — 크롬은 블러 없음 |
| `-webkit-backdrop-filter: …; backdrop-filter: …` | `backdrop-filter` 만 — 정상 |

지원 범위(Safari 26.5+, 표준은 18 부터)는 접두어 없이 되므로 붙일 이유도 없다. stylelint `property-disallowed-list` 로 막는다.

### D18. 2026-10-02 — Raw 팔레트를 테마마다 뒤집는 방식을 유지한다 (D11 의 테마 결정을 바꿈) → D20 으로 바뀜

D11 은 "Raw 팔레트는 테마와 무관해야 하고, 뒤집으면 이름이 거짓말을 한다"며 Raw 80개를 고정하고 Semantic 을
`light-dark()` 로 바꾸기로 했다. 업계 자료로 다시 보니 이건 두 방식 중 하나일 뿐이다.

| 방식 | 쓰는 곳 | 팔레트 이름의 뜻 |
|---|---|---|
| 팔레트 고정, 역할이 테마마다 다른 단계를 가리킴 | Material 3(ref 는 어디서나 같은 값) · Tailwind | 밝기 |
| 팔레트를 테마마다 뒤집음, 역할은 테마를 모름 | GitHub Primer(`base/color/light`·`dark` 가 따로 — `neutral-0` 이 라이트에서 흰색, 다크에서 검은색) · Radix(`gray1` 은 두 테마 모두 "앱 바탕") | 바탕 → 글자 쪽 순서 |

이 저장소는 이미 뒤에 것이다(`--color-neutral-0` 이 라이트 흰색, 다크 검은색). 이름이 거짓말을 하는 게 아니라 숫자의
뜻이 밝기가 아니라 순서였고, 명세가 그걸 적지 않았을 뿐이다. 앞의 방식으로 바꾸면 Raw 80개와 Semantic 전부를
다시 짜야 하는데 보이는 변화가 없다. D11 이 내세운 실제 이득(다크에서 스크롤바·폼이 어둡게)은 `color-scheme` 하나로
얻는다 — 그건 팔레트 방식과 무관하다. 그래서 뒤집기는 유지하고 이행 5단계는 `color-scheme` 만 남긴다.
그림자(`--shadow-*`)가 다크에서 더 진해지는 것도 같은 방식이다.

### D22. 2026-10-02 — 이행 4단계: 층 구조

- **층 순서 선언을 인라인 `<style>` 이 아니라 별도 CSS 파일로 바꿨다(명세 4-2 를 고침).** Next 는 CSS 파일마다 React 의
  `precedence` 그룹을 따로 만들어 `<head>` 에 넣는다. 레이아웃의 `<style precedence>` 가 그보다 앞에 온다는 보장이 없다.
  대신 레이아웃이 import 한 CSS 는 import 순서대로 root 청크에 들어가므로, 선언 한 줄만 담은 `layers.css` 를 첫 import 로 두었다.
  개발 서버에서 root 청크의 첫 줄이 이 선언인 것을 확인했다.
- 전역 CSS 는 `global.css` 의 `@import … layer(…)` 로 층에 넣었다. `tokens/_index.css` 처럼 안에서 다시 `@import` 하는 파일도
  가져온 내용이 함께 그 층에 들어간다(확인).
- **테마 전환 규칙은 층 밖에 남겼다.** 층에 넣으면 컴포넌트의 transition 에 지게 되어, 테마를 바꾸는 순간 일부 요소의 색이

- **편법(`.x.x` 198 · `!important` 327)은 이번에 걷지 않았다.** 공용 컴포넌트를 덮으려던 것은 이제 필요 없지만, 페이지 모듈끼리

- **확인**: 개발 서버에서 6개 화면 × 데스크톱/모바일의 모든 요소 계산값을 바꾸기 전과 비교했다. 원래 흔들리는 곳(로딩 화면 ·

- **색이 아닌 테마 값은 테마 블록에 둔다(2-5-1).** `light-dark()` 는 색만 받는다. 다크에서 검은 로고를 뒤집는 `filter: invert(1)` 은
  `_semantic.css` 테마 블록의 `--filter-mono-logo` 로 옮겼다. 처음에는 `mask-image` + `light-dark()` 색으로 바꾸려 했다.
  그런데 마스크 이미지는 CORS 로 받아야 하고, 로고 CDN(simpleicons)의 CORS 헤더를 이 환경에서 확인할 수 없어 접었다.
- **모양까지 다른 것은 겹쳐 그린다.**
  - 그림자의 퍼짐, Works 빈 화면의 배경 겹 수, 원통 인트로의 별(다크)과 꽃잎(라이트)이 여기에 해당한다.
  - 두 벌을 겹쳐 두고, 테마마다 한 벌의 색을 `transparent` 로 둔다.
  - 별 · 꽃잎은 요소 하나를 두 의사 요소로 나눴다. 각자 제 가운데를 축으로 깜빡이므로 예전과 같은 움직임이다.
- **특이도를 그대로 둔 곳.**
  - 코드 하이라이트 규칙 앞에 `:root` 를 붙여 특이도를 예전 `[data-theme] …` 과 같은 (0,2,x) 로 맞췄다.
  - 에디터는 클래스를 누적해 한 span 에 `hljs-string hljs-subst` 처럼 붙인다. 특이도를 낮추면 뒤에 있는 "기본색으로 되돌리는"
    규칙이 이겨 색이 바뀐다.
- **확인.**
  - 계산값 비교는 개발 서버에서 7개 화면 × (데스크톱 라이트 · 데스크톱 다크 · 모바일 다크)로 했다. 전역 클래스
    고정물(코드 하이라이트 전 토큰 · Shiki · 코드 바 · 강조 글)을 페이지에 넣고 모든 요소의 색 · 배경 · 테두리 · 그림자 ·
    transition 을 바꾸기 전 두 번, 바꾼 뒤 두 번 찍어 비교했다.
    - 남은 차이는 `color-scheme`, 지운 `.glass`(쓰는 곳이 없던 전역 클래스), `/design-system` 에서 지운 설명 한 문단뿐이었다.
    - 원래 흔들리는 곳(로딩 화면 · 글자 애니메이션)은 뺐다.
    - 같은 그림인데 계산값 표기만 달라진 곳이 하나 있다. 별똥별 선이 단색 → 같은 색 두 점 그라디언트가 됐다.
  - 이 환경에서 화면에 안 나오는 모듈(원통 배치 · Works 빈 화면 · ERD · 에디터 코드 바 · 기술 스택 아이콘 · 타자기)은
    master 의 CSS 와 지금 CSS 를 같은 DOM 에 각각 입혀 라이트/다크 스크린숏을 픽셀 비교했다.
    - 다섯은 같았다.
    - 별 · 꽃잎(34px · 최대 채널 차 3/255)과 에디터 코드 바 hover(53px · 6/255)는 안티에일리어싱 차이였다.
  - 히어로 배경은 사용자가 정한 색을 가정해 테마마다 풀린 값을 확인했다.
  - View Transition 은 콜백이 끝날 때 `data-theme` · 배경 · `color-scheme` 이 이미 바뀐 것, 길이 300ms, 움직임 줄이기에서
    바로 바뀌는 것을 확인했다.
  - DB 가 필요한 화면(글 상세 · 관리자)은 이 환경에서 열 수 없었다.

### D24. 2026-10-02 — 이행 6단계: 색

- **팔레트 값 — 미리보기 A 를 골랐다.**
  - 미리보기에서 두 가지를 비교했다. A 는 지금 쓰는 브랜드 · 상태색을 그대로 단계에 앉히고 사이만 채운다.
    B 는 모든 색상에 같은 명도 사다리를 쓴다.
  - B 는 간격이 고르다. 대신 브랜드 강조색을 포함한 대부분의 색이 ΔL 1–3.5 바뀐다.
  - A 와 지금의 차이는 거의 보이지 않았다. 브랜드 색이 그대로인 A 로 정했다.
- **A 에서 바뀐 값(보이는 변화).**
  - 라이트의 오류 글(`--text-error-strong`)이 `red-700` 으로 한 단계 진해졌다(L 55.1 → 51.1, 대비 4.97 → 5.89).
    예전 값만 따로 단계를 주면 600(L 57.7)과 너무 붙어 눈금이 망가진다.
  - 정보 글(`--text-info-strong`)은 정보 기본색과 합쳤다(L 53.6 → 54.6, 대비 4.78).
  - 강조 반투명의 바탕이 라이트에서 강조색과 같은 값이 됐다(L 55.96 → 55.2). 예전 투명도 토큰만 따로 값을 갖고 있었다.
  - 라이트의 밝은 강조(accent-light)는 다크 강조와 같은 단계(`accent-500`)로 합쳤다(ΔL 0.1).
  - 성공 바탕 `--bg-success` 는 예전 값이 팔레트 밖이라 `green-400` 으로 옮겼다(ΔL 1.7).
- **에디터 글자색 — 미리보기의 "가"(팔레트를 따른다)로 정했다.**
  - 예전 글에 저장된 `var(--color-red-500, #ef4444)` 는 그동안 대체값(Tailwind 색)으로 보였다.
    이제 같은 이름의 팔레트 단계가 생겨 팔레트 색으로 보인다(ΔE 0.2–4.7).
  - 보라(`purple`)는 팔레트에 없어 예전 글은 대체값 그대로다. 새로 고르는 보라는 `violet-500` 이다.
- **사이트 설정의 테마 색은 역할을 덮어쓴다.**
  - 예전에는 `themeColors.ts` 가 팔레트(`--color-accent` · `--color-neutral-*` · 투명도 단계)를 지금 테마 값으로 덮어썼다.
    팔레트를 고정하면서 역할을 덮어쓰도록 바꿨다. 덮어쓰는 역할은 강조 면 셋, 무채색 역할 여섯, `--text-contrast` 다.
  - 다크의 사용자 테마에서 대화상자 바탕이 흰색이던 것(예전 `--color-neutral-0` 을 늘 흰색으로 덮어썼다)은 이로써 없어졌다.
- **역할 하나를 읽는 코드.** 관리자 콘텐츠 탭이 `getComputedStyle().getPropertyValue("--bg-primary")` 로 색을 읽었다.
  역할 토큰이 `light-dark()` 를 담으면서 이 값은 풀리지 않은 식이 된다. 그래서 요소에 색으로 입혀 풀린 값을 읽도록 바꿨다.
- **그림 색.**
  - Works 빈 화면의 돔 · 은하수 · 꽃잎, 코드 창 신호등, HTTP 메서드 색, 컬러 피커의 색 공간은 테마를 따르는 UI 색이 아니다.
    그래서 팔레트에 맞추지 않고 값 그대로 컴포넌트 토큰으로 모았다.
  - 마스크의 `#000` 은 색이 아니라 알파라서 감시 테스트에서 뺐다.
  - 그림자 안의 색(71)은 9단계에서 그림자 토큰과 함께 옮긴다.
- **대비 표.** 토큰 표 끝에 역할 쌍 22개의 대비를 두 테마로 생성한다. 미달 셋(라이트의 성공 · 정보 배지 글, 경고 점)은
  이행 전부터 있던 값이다. 고치면 보이는 변화라 이번에 바꾸지 않았다.
- **확인.**
  - 개발 서버에서 7개 화면 × 세 조합(데스크톱 라이트 · 데스크톱 다크 · 모바일 다크)을 비교했다. 모든 요소의 색 계산값을
    바꾸기 전 두 번, 바꾼 뒤 두 번 찍었다. 색은 OKLab 거리로 비교했다(`color-mix()` 결과는 표기가 달라진다).
  - 남은 차이는 위의 강조 반투명 바탕(ΔE 0.8), 밝은 강조(ΔE 1.5), 그리고 다시 짠 `/design-system` 팔레트 절뿐이었다.
  - 프리셋을 눌러 사용자 테마 색이 역할 · 반투명 역할에 퍼지는 것도 확인했다.

### D25. 2026-10-02 — 이행 7-1단계: 글꼴 역할 · 제목 단계

- **글꼴은 Pretendard 하나로 정했다(미리보기로 고름).**

  - Pretendard 의 영문은 Inter 를 바탕으로 만들어 Inter 와 거의 같다. 한글 · 영문이 한 글꼴이라 높이 · 굵기가 맞고 웹폰트가 하나 준다.

    통일을 골랐다.

  따랐고, 페이지 기본 글꼴(body)은 설정과 무관한 Inter 였다. 기본값을 Pretendard 로 바꾸고 목록에 넣었다. Space Grotesk 는 고를 수 있는
