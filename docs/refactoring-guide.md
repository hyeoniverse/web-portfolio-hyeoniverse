# 리팩토링 방법론

**이 프로젝트를 리팩토링할 때마다 따르는 원칙과 진행 방식이다.** 특정 작업이 아니라
방법을 담는다 — 라운드가 바뀌어도 그대로 쓴다. 리팩토링에 손대기 전 이 문서를 먼저 읽는다.

> **진행 중인 라운드의 현황**(어느 단계까지 했는지·실행 PR·성과 수치·발견한 결함)은
> 문서가 아니라 **상위 트래킹 이슈**에서 관리한다. 현재 라운드: **[#388](https://github.com/hyeoniverse/web-portfolio-oval/issues/388)**.
> 각 단계를 왜 그렇게 했는지(회고)는 그 단계를 실행한 PR 본문에 있다.

## 0. 왜 방법론이 필요한가

`src` 가 22만 줄이 넘는다. 한 번에 리팩토링할 수 없고, 한 번으로 끝나지도 않는다 —
새 기능이 쌓이면 또 거대 파일과 죽은 코드가 생긴다. **그때마다 처음부터 고민하지 않도록**
원칙·안전망·진행 순서를 고정해둔다.

착수 시점의 규모를 감으로 잡아두면(라운드마다 갱신되는 값이라 참고용):

| 항목 | 첫 라운드 착수 시점 (2026-07) |
| --- | --- |
| `src` 전체 | 226,886줄 (tsx 432 · ts 375 · css 214) |
| `use client` | 353 / 432 tsx (82%) |
| `any` / `eslint-disable` | 308 / 348 |
| 최대 파일 | PlateEditor 3,561 · admin page 3,035 · WorkEditor 2,610 |
| 최대 CSS | Settings.module.css 6,633 |

구조 규약(3-tier 토큰, `components/ui`, `_components` 콜로케이션)은 이미 서 있다.
반복해서 문제가 되는 것은 **규약을 못 따라간 거대 파일들과 client 경계**다.

## 1. 원칙

### P1. 리팩토링 커밋에 기능 변경을 섞지 않는다

`refactor:` 커밋은 동작이 100% 같아야 한다. 픽셀도 보존한다.
리팩토링 중 발견한 버그는 **이슈로 떼고 별도 PR**. 롤백 가능성이 여기서 갈린다.

### P2. 한 번에 한 축만

JSX 구조 · 스타일 · 프로젝트 구조 · 성능 · 타입을 한 PR에 섞지 않는다.
예외: Phase 4의 거대 파일 분해는 JSX와 CSS 모듈이 물리적으로 붙어 있으므로 함께 간다.

### P3. 측정 없는 성능 개선 금지

라우트별 First Load JS를 먼저 기록하고, 전/후 수치를 PR 본문에 적는다. 체감으로 판단하지 않는다.

```bash
npx next build --experimental-analyze   # ← npm run analyze 아님 (아래 주의)
```

**주의:** `npm run analyze`(`@next/bundle-analyzer`)는 이 프로젝트에서 **아무것도 생성하지 않는다.**
Next 16의 빌드는 Turbopack이 기본이고 bundle-analyzer는 webpack 플러그인이라 무시된다.
기준선과 측정 방법은 [perf-baseline.md](perf-baseline.md) 참조.

### P4. 원칙은 린터로 강제한다

문서로만 둔 규칙은 반드시 회귀한다. `audit:full`에 게이트를 얹어 기계가 지키게 한다.
새 규칙은 baseline을 락하고 **점진적으로 조인다** (한 번에 통과 불가능한 룰은 무시당한다).

### P5. 수직 슬라이스로 자른다

도메인 단위로 자르고, 한 슬라이스는 착수 → 완료 → 머지까지 끝낸 뒤 다음으로 간다.
**동시 진행 금지.** (도메인 순서는 [진행 방식](#4-진행-방식) 참조)

### P6. 보이스카웃 금지, 배치로 처리

지나가다 고치면 diff가 오염되어 리뷰가 불가능해진다.
눈에 띈 건 슬라이스 이슈의 체크리스트에 적고 해당 차례에 처리한다.

### P7. 삭제 > 추상화

추상화를 만들기 전에 `npm run knip`. 안 쓰는 코드를 지우는 게 가장 싸고 안전하다.
중복은 **3번째 등장할 때** 추출한다. 2번은 놔둔다.

### P8. 슬라이스마다 안전망을 먼저

손대기 전에 그 영역의 스냅샷을 확보한다. 없으면 리팩토링이 아니라 도박이다.

## 2. 안전망 4종

작업 전 순서대로 통과시킨다.

| 종류 | 대상 | 시점 |
| --- | --- | --- |
| `npm run audit:full` | typecheck · eslint · stylelint · knip | 매 커밋 (husky) |
| `npm run test:smoke` | 공개 라우트 13개 × 2 viewport | PR마다 |
| 유닛 테스트 | 손댈 `lib`/`utils`/`hooks`의 순수 로직 | 슬라이스 착수 전 보강 |
| 수동 QA 체크리스트 | 스모크가 못 덮는 영역 | 머지 전 |

스모크 e2e 는 픽셀 비교가 아니라 **깨짐만** 잡는다(페이지 로드·런타임 에러·에러 바운더리·빈 화면). UI 변경 자체는 허용하므로 — 이 프로젝트는 '변경 OK, 깨짐만 방지' 방침이라 픽셀 단위 시각 회귀는 걷어냈다. 리팩토링이 화면을 살짝 바꾸는 건 P1 위반이 아니다.

**중요 — 스모크에도 사각지대가 있다.** 렌더/에러만 보고 레이아웃 붕괴·스타일 손실 같은 "안 깨졌지만 이상함"은 못 잡으니, 큰 스타일 변경은 수동 QA 로 확인한다. `/admin/*` 은 로그인 세션 셋업이 필요하다.
사각지대 목록과 이유는 [perf-baseline.md](perf-baseline.md#커버리지-한계--아래는-시각-테스트로-못-잡는다) 참조.
**그 영역은 수동 QA 체크리스트가 유일한 안전망이므로 슬라이스 착수 시 반드시 작성한다.**

## 3. 코드 기준선

Phase 4에서 파일을 분해할 때 목표치. 절대 규칙이 아니라 **넘으면 분해를 검토하는 선.**

| 대상 | 상한 |
| --- | --- |
| 컴포넌트 파일 | 300줄 (한 화면에 안 들어가면 책임이 둘 이상) |
| CSS 모듈 | 500줄 |
| 컴포넌트당 `useState` | 7개 (넘으면 `useReducer` 또는 상태 분리) |
| JSX 중첩 | 5단계 |
| 파일당 export 컴포넌트 | 1개 (아이콘·프리미티브 모음 예외) |

### JSX 구조 규칙

- 조건부 렌더링은 삼항 중첩 금지 → early return 또는 서브컴포넌트로 분리
- `map` 안의 JSX가 5줄 넘으면 컴포넌트로 추출
- props 8개 이상이면 객체로 묶거나 컴포넌트 합성으로 재설계
- 파생 상태를 `useEffect`로 동기화하지 않는다 → 렌더 중 계산 또는 `useMemo`

### 스타일 규칙

기존 [design-system.md](design-system.md)의 3-tier 토큰 규약을 따른다. 추가로:

- CSS 모듈은 담당 컴포넌트와 1:1. 컴포넌트를 쪼개면 CSS도 함께 쪼갠다
- 셀렉터 중첩 3단계 이하
- 미사용 클래스는 슬라이스 완료 시 제거

<a id="스타일-축소"></a>
### 스타일 축소(compact) 기준

거대 CSS 모듈을 줄일 때의 판단 기준. **"줄인다"에 꽂혀 결합도를 올리거나 특이도를 높이면
오히려 나중에 더 비싸진다.** 무엇을 하고 무엇을 하지 않을지 명시한다.

**✓ 한다**

- **같은 역할 클래스만 통합.** 본질적으로 같은 것(예: 모든 stat 숫자 = 같은 mono 폰트)만.
  우연히 지금 같아 보이는 것은 놔둔다 — P7("중복은 3번째 등장할 때 추출").
  성급히 묶으면 하나만 바뀔 때 되돌리는 비용이 통합 이득보다 크다.
- **자연 상속되는 재선언을 지운다.** 폰트·색은 자식으로 상속된다. 부모가 이미 주는 값을
  자식에서 다시 선언한 곳을 제거하는 게 compact 의 핵심이다.
- **반복 조합은 그대로 둔다.** `display:flex; align-items:center` 류는 관용구라 각 module 에
  인라인한다. 값이 흔들리는 것은 gap·padding 을 토큰으로 맞추면 충분하다. 같은 구조가
  3곳 이상 반복되면 React 컴포넌트로 추출한다 — design-system §0-3.
- 자식 선택자(`.parent .child`)로 계층 표현 — design-system 3장 규칙.
  단, 전역 테마 트랜지션을 이겨야 하는 경우 외에는 **특이도를 낮게 유지**한다.

**✗ 하지 않는다**

- **`inherit` 를 "적극" 늘리지 않는다.** 폰트·색은 어차피 상속되므로 명시 `inherit` 는
  값의 출처만 흐린다. 방향은 반대 — 불필요한 재선언 제거.
- **스타일 통합 목적으로 global `id`(`#foo`) 를 만들지 않는다.** id 는 특이도 `(1,0,0)`
  으로 override 가 지옥이 되고, 페이지당 1개라 재사용 불가, CSS Modules 격리를 깬다.
  전역 스타일이 필요하면 **`:global(.class)`** 를 쓴다 (이 프로젝트가 이미 쓰는 방식).
  > `#modal`·`#modal-root` 가 id 인 것은 예외다 — React portal 의 mount point 라
  > 컴포넌트가 그 id 를 직접 붙인다(`Modal.tsx`). 스타일 통합의 모범이 아니다.
- **공유 유틸 클래스나 파일 간 `composes` 로 규칙을 묶지 않는다.** 다른 파일에서 가져온
  클래스와 자기 클래스는 특이도가 같아 프로덕션 번들 순서로 승자가 정해지고, 파일을 나누거나
  옮기기만 해도 모양이 뒤집힌다(#632). 같은 파일 안 `composes` 도 두 단계부터는 Turbopack 이
  끝 클래스를 안 붙인다. 상세는 design-system §3.
- **과도한 DRY.** 결합도 > 중복 제거 이득이면 놔둔다.

**전역 CSS(`styles/globals`) 정리는 슬라이스와 섞지 않는다.** 전 페이지에 영향이고
시각 회귀 사각지대가 커서 지금 건드리면 회귀를 못 잡는다. 슬라이스를 돌며 "각 컴포넌트가
전역 스타일을 어떻게 쓰는지" 근거를 모은 뒤, **별도 작업**으로 처리한다 (P2·P8).

<a id="배치-기준"></a>
### 컴포넌트 배치 기준

파일을 어느 폴더에 둘지의 규칙. **쓰는 라우트 수로 판단한다.**

| 위치 | 용도 |
| --- | --- |
| `src/components/ui` | 도메인 무관 프리미티브 |
| `src/components/<domain>` | **2개 이상 라우트**에서 쓰는 도메인 컴포넌트 |
| `src/app/<route>/_components` | 해당 라우트 전용 |

**1개 라우트에서만 쓰면 그 라우트에 콜로케이션, 2개 이상이면 `components/<domain>` 으로 승격.**

"파일 하나에서만 import 되면 콜로케이션" 이 아니다. 부모 컴포넌트를 쪼개서 생긴 자식은
import 되는 곳이 1곳이어도 그 자리가 맞다. **파일 수가 아니라 라우트 수로 센다.**

`lib`(서버 의존·데이터 접근·도메인 로직) vs `utils`(순수 함수) 도 같은 맥락 —
`process.env`·Supabase·`next/headers` 를 쓰면 `lib`, 아니면 `utils`.

## 4. 진행 방식

리팩토링은 6단계로 진행한다. **Phase 0~3 은 라운드마다 반복하는 준비·공통 작업이고,
Phase 4 가 실제 도메인 코드 분해(전체의 약 70%)다.**

| Phase | 하는 일 | 왜 이 순서인가 |
| --- | --- | --- |
| <a id="phase-0"></a>0 기준선 | 시각 회귀·번들 등 안전망과 계측 기준선 확보 | 손대기 전 스냅샷이 없으면 회귀를 못 잡는다 (P8) |
| <a id="phase-1"></a>1 게이트 | 품질 지표를 현재 수준에 락 (나빠지면 CI 실패) | 이후 대량 작업 중 품질이 조용히 후퇴하는 걸 막는다 (P4) |
| <a id="phase-2"></a>2 성능 | 전 라우트 공통 비용부터 줄인다 | 파일 수는 적고 효과는 전 페이지에 걸려 ROI 가 가장 크다 |
| <a id="phase-3"></a>3 구조 | 파일 배치·경계를 조사 (문제 없으면 이동 안 함) | 배치 규칙은 [코드 기준선](#배치-기준)에 있다. diff 만 큰 이동은 피한다 (P6) |
| <a id="phase-4"></a>4 슬라이스 | 도메인 단위로 거대 파일을 분해 | 한 도메인씩 착수→완료→머지 (P5). 아래 참조 |
| <a id="phase-5"></a>5 잠금 | 게이트를 warn→error 로 승격 | 개선한 만큼 되돌아가지 못하게 못 박는다. 승격 판단은 [아래](#phase-5--승격-판단은-규칙-이름이-아니라-위반-내용으로) |

### Phase 5 — 승격 판단은 규칙 이름이 아니라 위반 내용으로

경고를 오류로 올리려면 그 규칙의 위반이 0 이어야 한다. 그래서 "위반을 다 고치고 올린다" 로
접근하기 쉬운데, **고치기 전에 위반을 전수 확인하는 순서가 먼저다.** 규칙이 잡은 것이
정말 지금 코드의 문제인지부터 본다.

실제로 확인해 보니 세 부류가 나왔다.

- **고치면 코드가 좋아지는 것** — 올린다. 렌더 중 `Date.now()`, deps 누락,
  렌더 안에서 컴포넌트 정의 같은 것들이다.
- **다른 도구를 전제한 것** — 올리지 않는다. `preserve-manual-memoization` 은
  React Compiler 가 최적화를 건너뛴다는 안내인데 이 프로젝트는 Compiler 를 쓰지 않는다.
  규칙을 맞추려면 deps 를 오히려 덜 정확하게 만들어야 하는 자리도 있었다.
- **규칙이 상황을 구분하지 못하는 것** — 올리지 않는다. `immutability` 는 렌더 중 변경과
  콜백 안 변경을 구분하지 못해, `useRef` 를 정상적으로 쓰는 코드까지 잡는다.

**올리지 않기로 했으면 그 판단을 규칙 옆에 적는다.** 남은 위반 개수만 보고 다음 사람이
같은 조사를 반복하거나, 규칙을 맞추려다 코드를 나쁘게 만드는 걸 막기 위해서다.
`eslint.config.mjs` 의 warn 목록에 각 규칙이 왜 아직 warn 인지가 적혀 있다.

`set-state-in-effect`·`refs` 는 위반이 많아 부류별로 나눠 고칠 부류만 고쳤다([#695](https://github.com/hyeoniverse/web-portfolio-oval/issues/695)).
같은 부류를 새로 쓰지 않도록 `src/hooks` 에 공용 훅을 둔다.

- 클라이언트에서 그리는 중인지 → `useHasMounted`
- props 를 따라가되 사용자가 잠깐 바꿀 수 있는 상태 → `useStateFromProp`
- 어떤 값이 바뀌면 상태를 맞추거나 되돌리기 → `useDepsChanged` 로 렌더 중에 맞춘다
- 효과·이벤트 처리·타이머에서 읽을 최신 값 → `useSyncRef` (ref 는 부르는 쪽에서 `useRef` 로 만든다)
- 화면에 쓰는 값 → ref 가 아니라 상태

승격했으면 **일부러 위반을 넣어 CI 가 실제로 서는지 확인한다.** 설정만 바꾸고 넘어가면
규칙 이름 오타나 다른 설정에 덮여 안 걸리는 걸 모른다.

### Phase 4 — 도메인 슬라이스 순서

`admin → posts → about·works → 에디터` 순으로 하나씩. 한 슬라이스를 착수부터 머지까지
끝낸 뒤 다음으로 간다 (P5, 동시 진행 금지).

**각 도메인의 상세 계획(조사·안전망·분해 순서)은 그 슬라이스에 착수할 때 세운다.**
미리 다 세우지 않는 이유:

- 그 도메인을 실제로 조사해봐야 안전망과 분해 순서를 정할 수 있다 (P8)
- 앞 슬라이스에서 배운 패턴을 다음에 적용하는 게 낫다 — 미리 짠 계획은 낡는다 (P6)

그래서 **이 방법론 문서에는 도메인별 상세가 없다.** 진행 중인 슬라이스의 계획과
파일 목록은 그 슬라이스 이슈에서 본다 (현재 라운드 트래킹: [#388](https://github.com/hyeoniverse/web-portfolio-oval/issues/388)).

## 5. PR 규약

- 슬라이스당 이슈 1개, PR 여러 개. PR 본문에 `Refs #N` (슬라이스 완료 PR만 `Closes #N`)
- PR 1개 = 300~500줄 목표
- 커밋 타입: 동작 보존 = `refactor:`, 시각 조정만 = `design:`, 구조 이동 = `refactor:`
- PR 본문 필수 항목:
  - 변경한 축 (JSX / 스타일 / 구조 / 성능 / 타입 중 하나)
  - 시각 회귀 diff 결과
  - 성능 PR인 경우 First Load JS 전/후 수치
